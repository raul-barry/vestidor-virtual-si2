# Local SaaS demo bootstrap

These commands are for a local development/test database only. The demonstration seed refuses `ENVIRONMENT=production`, preserves existing users and business records, and refuses to replace a tenant's existing active plan.

## First global platform administrator

1. Apply migrations from the backend directory: `python -m alembic upgrade head`.
2. Set `PLATFORM_ADMIN_EMAIL` and `PLATFORM_ADMIN_PASSWORD` in the process environment, or run `python -m app.database.bootstrap_platform_admin` and enter the email/password at its prompts. Use a unique email and a password of at least 12 characters. The password is hashed with the application's existing bcrypt password context.
3. Run `python -m app.database.bootstrap_platform_admin`.
4. Sign in through the existing `/api/auth/login` route with those credentials. The returned access token has a null organization scope; platform endpoints authorize it by the `ADMINISTRADOR_PLATAFORMA` role.

The bootstrap is idempotent for the same global account. It will not promote an organization user, change an existing password, or create a second platform administrator. There is no public privilege-assignment endpoint.

## Synthetic SaaS data

Set `DEMO_SEED_PASSWORD` securely in the environment (minimum 12 characters), then run `python -m app.database.demo_data_seed`. Synthetic customer and staff accounts use tenant-specific `@demo.test` addresses and the supplied password; existing accounts are not updated. Do not put the password in source control or command history.

The seed creates/finishes FashionStore (Estilo, 2 branches), UrbanVogue (Moda, 3 of at most 10 branches), and Elegance Boutique (Glamour, 3 branches). It creates 18 synthetic users, 15 products, size/color variants, branch inventory, active carts, pending reservations, historical demo sales, and one exchange request per organization. Historical paid sales are passed through `PaymentService` and the existing explicitly simulated QR provider. Demo payment references are generated by that provider and are never bank references. No external payment is submitted. The seed suppresses automatic business audit entries for seed-created rows; it does not manufacture AuditLog records.

Seeded order delivery references beginning `DEMO-SEED:` identify synthetic sales. Historical sales are placed at weekly intervals over 84 days so the current demand dashboard has multiple observations per product and branch. The analytics implementation remains the existing seasonal-average/trend method.

The seed is additive and resumable: repeated runs use deterministic tenant-scoped names, emails, SKUs, order markers, and exchange UUIDs. It does not delete or rewrite other data. A tenant with more active branches than its requested demo target, or an active subscription on a different plan, causes the seed to stop rather than changing that state.
